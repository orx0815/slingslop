# Webcache configuration

The webcache is the reverse-proxy / caching tier in front of Sling on the public
domains. It turns an otherwise ~2k req/s Sling into tens of thousands of req/s.
Its per-tenant config is **generated by CONGA** from one `tenant:` block — ops
never hand-writes a vhost, in prod, the Ansible/vagrant local harness, or the
`devops/docker-compose.yml` quickstart (both use the `local-webcache` env).
(A *tenant* is a host → content-root mapping; it
usually maps to its own app, but several tenants can reuse one app at different
content roots — see `appsRoot` below, and devops/conga/README.md.) For the
deployment mechanics (how the generated files reach the box), see
[devops/README.md](README.md) §6.

```
Browser ──► Traefik ──► webcache ──► Sling (slingslop:8080)
            (TLS,        (cache +      (HTL render + JCR)
             auth,        URL rewrite +
             rate-limit)  Sling filter)
```

TLS termination, HTTP basic-auth (editor) and rate-limiting live at **Traefik**.
The webcache is responsible only for **caching**, **URL shortening** and
**Sling-aware request filtering**.

## Three cache engines — one parameter set

The `slingslop-webcache` role ships **three interchangeable implementations** of
the same job, selected per node with `variant:`:

| Variant | Engine | Cache | Request-coalescing (cold-cache stampede) |
|---|---|---|---|
| `apache` (default, in prod) | httpd `mod_cache` + `mod_proxy` | disk | ❌ none |
| `nginx` | nginx `proxy_cache` | disk | ✅ `proxy_cache_lock` |
| `varnish` | Varnish VCL | RAM | ✅ native |

All three read the **exact same tenant parameters** (defined once in
[`devops/conga/src/main/roles/slingslop-app-base.yaml`](conga/src/main/roles/slingslop-app-base.yaml))
and render them in each engine's own syntax, so switching engine is a one-line
change — the per-app rules stay identical:

```yaml
nodes:
- node: vps1
  roles:
  - role: slingslop-webcache
    variant: nginx        # apache | nginx | varnish
```

Output filenames differ only so the three defs don't collide inside CONGA:
apache → `<app>.conf`, nginx → `<app>.nginx.conf`, varnish → `<app>.vcl`. A node
runs one variant, so its `webcache/` dir holds only that engine's files.

**Deployment picks the engine up automatically — `variant:` is the only
setting ops ever touches.** CONGA also renders a node-level marker file
(`env/webcache-variant-apache|nginx|varnish`, one of the three, matching
whatever `variant:` was set). The Ansible `webcache` role stats for whichever
marker exists and sets a `webcache_variant` fact from it; the `traefik` role's
`compose.edge.yml.j2` then picks the right image, cache volume / bind-mount
target, healthcheck and startup command purely from that fact — there is no
second place to keep in sync, and deploying the wrong image for the rendered
config is a hard `ansible.builtin.fail` (missing marker), not a silent
mismatch. Varnish additionally only supports **one** tenant's `.vcl` per node
(see the note below) — the `webcache` role stages that single file at a fixed
path and fails fast if zero or more than one is found.

> **Varnish note.** Varnish loads **one** VCL per instance, so each generated
> `<app>.vcl` is a complete single-host VCL. To run several tenants on one
> Varnish node, compose their per-app blocks (the `backend` + the host-guarded
> branch of `vcl_recv`) into one outer VCL. The apache/nginx variants have no
> such limit — their per-app `*.conf` files are simply all included.

## What the webcache does

### 1. HTTP caching

Cache successful responses and serve them without touching Sling. Key policy:
**one cache entry per PATH, ignoring the query string** (`htmlTtlSeconds` /
`staticTtlSeconds` control the TTLs). The full request (incl. query) is still
forwarded to Sling on a MISS, so Sling sees the params — but every `?v=<token>`
(ours) and `?x=rnd` (attacker) collapses to one entry: cache-buster-safe **and**
immune to query-string cache-bypass DoS.

- Apache: `CacheIgnoreQueryString On`
- nginx: `proxy_cache_key "$scheme$request_method$host$uri"` (no `$args`)
- Varnish: `vcl_hash { hash_data(regsub(req.url, "\?.*$", "")); }`

### 2. URL shortening — three inbound forms

All three resolve to the long form before hitting Sling:

| Inbound | Meaning |
|---|---|
| `/home.html` | fully shortened (correct Sling resource mappings) |
| `/sling-matrix/home.html` | half — `ResourceResolver.map()` only cut `/content` |
| `/content/sling-matrix/home.html` | long — passes through unchanged |

Outgoing `Location` redirects are cleaned too (the internal backend host is
stripped, so 30x don't leak `sling:8080`).

### 3. Sling-aware request filtering (the front-line protection)

Web servers don't understand Sling URLs, e.g.
`/content/x/page.a.b.html/suffix/foo.json` has extension **html**, not json (the
`.json` is inside the *suffix*). The filters compute the **true extension** — the
first `.ext` before the suffix `/` — then apply, all driven by the shared params:

- **method allowlist** (`allowedMethods`) — only `GET`/`HEAD`; others → 405.
- **selector / internal blacklist** (`denySelectors`, `denyPathPrefixes`) —
  `.infinity.json` dumps, numbered json, `sysview`/`docview`, `/system`, `/bin`,
  `/crx`, `/libs/granite` → 403.
- **`.json` allowlist** (`jsonAllowlist`) — a `.json` extension is served only
  under explicitly allowed path prefixes; everything else → 403.
- **uncached patterns** (`uncachedPatterns`) — always fetched fresh.

## Per-tenant cache & security rules

Every public host is a **CONGA `tenant:` block** (a tenant is a host →
content-root mapping, not necessarily its own app). Beyond the routing basics
(`contentRoot`, `appsRoot`, `subdomain`, `homePage`), each tenant can tune the
cache/vhost tier with these **shared** knobs. All are optional — the defaults
suit a normal public HTML site. Set them per tenant in the environment file:

| Param | What it does | Default |
|---|---|---|
| `appsRoot` | The app's `/apps` clientlib root, always passed through **unrewritten** (css/js). Must match where the app serves scripts; override when a tenant reuses another app (e.g. `zen` → `/apps/slingslop/zengarden`) or the root differs (e.g. `/apps/<tenant>`). Wrong value → 404'd css/js. | `/apps/slingslop/${tenant}` |
| `serverAliases` | **Add more domains** the app answers for (on top of `<subdomain>.<domain>`). | `[]` |
| `passthroughPaths` | **Allow list** — extra path prefixes that reach Sling **unrewritten** (short-URL re-expansion skipped). `${appsRoot}` is always allowed. | `[]` |
| `jsonAllowlist` | Path prefixes under which a `.json` **resource extension** is allowed. Everything else ending in a `.json` extension is denied. Empty = no JSON exposed. | `[]` |
| `denySelectors` | Sling selector / view names always blocked (`.infinity.` dumps, `.sysview.`, …). | `infinity, tidy, sysview, docview, children, query` |
| `denyPathPrefixes` | Internal JCR trees never reachable through the cache. | `system, bin, crx, libs/granite` |
| `uncachedPatterns` | **Uncached paths / selectors / extensions** — regexes that must never be cached (still proxied, always fresh). | `[]` |
| `allowedMethods` | HTTP methods forwarded to Sling; anything else → 405. | `GET, HEAD` |
| `htmlTtlSeconds` / `staticTtlSeconds` | Cache lifetime for HTML-ish vs. long-lived static assets (images/fonts). | `10` / `2592000` |
| `cssJsTtlSeconds` | Cache lifetime for css/js specifically. Defaults to `staticTtlSeconds` (assumes fingerprinted clientlib URLs); override to a short value (e.g. `300`) for apps with no cache-busting on their css/js, like `zengarden`/`zen`, so a deploy is picked up quickly. | `${staticTtlSeconds}` |
| `flushToken` | Shared secret for the internal `:8088/flush?prefix=...` endpoint (see "Selective cache flush" below) — same value, same effect on all 3 engines. Apache/nginx read it as a `FLUSH_TOKEN` container env var (`webcache_flush_token` Ansible group_var); Varnish has no env-var access from VCL, so it's baked straight into the generated `.vcl` instead. Empty = no token required (docker-network isolation is the primary control on every variant). | `""` (disabled) |

Worked example — a tenant that adds an apex-domain alias, exposes a JSON API,
keeps a live fragment uncached and lets a servlet path through unrewritten:

```yaml
tenants:
- tenant: shop
  roles: [ public-cached ]
  config:
    contentRoot: /content/shop
    subdomain: www
    serverAliases: [ "${domain}" ]          # add more domains
    passthroughPaths: [ /bin/public ]        # allow list → Sling, unrewritten
    jsonAllowlist:                           # where .json is allowed
    - /content/shop/api/
    - "/apps/[^/]+/api/"
    uncachedPatterns:                        # never cache these
    - "^/content/shop/live"
    - "\\.nocache\\."
```

Rebuild (`mvn -pl devops/conga clean package`) and the same values land in the
apache / nginx / varnish output — whichever variant the node runs. Need a knob
that doesn't exist yet? See [conga-handlebars-101.md](conga-handlebars-101.md).

## Gotchas (hard-won)

- **`Accept-Encoding` cache-variant trap.** Apache `mod_cache` keys on the exact
  `Accept-Encoding` string, so a stale entry cached under Chrome's
  `gzip, deflate, br, zstd` was served to browsers while `curl` (a different
  header) got a fresh MISS — making the staleness invisible. nginx/Varnish
  normalise it to `gzip|""`.
- **Cache persistence cuts both ways.** Apache/nginx **disk** caches survive a
  restart (which is how a month-old asset lingered). Varnish is **RAM only** →
  cold after restart.
- **Deploys don't flush the proxy.** The prod deploy recreates only the Sling
  container, not the webcache, and the cache volume persists — so a changed asset
  can serve stale until the URL changes (cache-buster) or you flush. See
  "Selective cache flush" below, or nuke the whole disk cache:
  `docker exec slingslop-webcache sh -c 'rm -rf /var/cache/httpd/slingslop/*'`
  (safe while Apache runs — the next request per URL is just a fresh MISS).

## Selective cache flush — same endpoint on all 3 engines

All three variants expose the **identical** internal-only contract, so Sling
(or any caller) never needs to know which engine is running:

```
GET/POST http://webcache:8088/flush?prefix=/apps/sling-matrix/
GET/POST http://webcache:8088/flush?prefix=/content/sling-matrix/home.html
```

- `prefix` must match `^/(apps|content)/[A-Za-z0-9/_.-]+$`, else 400.
- Reachable only on the docker network — a **separate `:8088` listener**,
  never published to the host or routed by Traefik.
- Optional shared secret: set `flushToken` (CONGA tenant/role param — see the
  table above) to also require an `X-Flush-Token: <token>` header; empty
  (default) = network isolation is the only control.
- Success → `200`; bad/missing `prefix` → `400`; disallowed client → `403`;
  hitting `/flush` on the public `:80` listener → `404` (confirmed for all 3
  engines during verification).

**Not yet wired up from the app** — nothing calls this today (e.g. on a
content publish event). It's available as a primitive; hooking it into a
deploy or publish workflow is a follow-up.

How each engine implements the same contract underneath:

- **apache** (`devops/webcache/`): `flush.cgi` + `flush.conf` expose the
  endpoint via `mod_cgid`. mod_cache_disk names files by a hash of the cache
  key (`CACHE_ROOT/<a>/<b>/<hash>.header|.data`), not by URL path, so
  `purge-cache.sh` greps the `.header` files (they store the original request
  URL) for the substring and deletes matching pairs. No Apache reload needed.
- **varnish** (`devops/conga/.../varnish/app.vcl.hbs`): a `vcl_recv` branch
  guarded by `std.port(local.ip) == 8088` parses `prefix` off the query string
  and calls Varnish's native `ban("obj.http.X-Url ~ ^" + prefix)` — every
  cached object is tagged with its own URL (`beresp.http.X-Url`) precisely so
  bans can match by prefix ("ban-lurker friendly"). No script, no reload.
- **nginx** (`devops/webcache-nginx/`, OpenResty): stock `nginx:alpine` has no
  purge module or scripting hook, so this variant is built on OpenResty
  instead — an internal `server { listen 8088; }` block's
  `content_by_lua_block` shells out to `purge-cache.sh`, adapted to nginx's
  single-file-per-entry cache format (matches the `KEY:` line each cache file
  stores). `CACHE_ROOT` defaults to `/var/cache/nginx` (the parent of every
  tenant's own `proxy_cache_path` zone), so one script instance covers all
  tenants on that node.

All three were verified end-to-end on a throwaway local rig (real backend +
real engine container): cache a URL, flush its prefix, confirm the next
request is a fresh MISS serving updated content, and that a wrong/missing
prefix or the public `:80` listener are correctly rejected.

Not wired into the ansible/compose deployment (only `apache` is; nginx/varnish
are generated-config-only today, see the CONGA docs) — this is the standalone
image, built and run the same way as `devops/webcache/`.

## Benchmark

Indicative numbers (`hey -n 50000 -c 500`, single hot URL, warmed, loopback):

| Tier | Requests/sec | vs Sling |
|---|---:|---:|
| Sling (uncached) | ~2,150 | 1× |
| Apache | ~25,700 | ~12× |
| nginx | ~28,000 | ~13× |
| **Varnish** | **~97,700** | **~45×** |

Best-case (all-HIT, one URL); real traffic has misses and URL variety. Varnish's
lead is mostly **RAM vs disk** plus its worker model — but it is RAM-bound
(size `VARNISH_SIZE` to the hot set; keep the 1-year image renditions out) and
**cold on restart** (prefer `varnishadm vcl.load`/`vcl.use` over a container
recreate). Before switching prod, test against **realistic URL variety** and
exercise a few malicious `.json`/selector probes to validate the filters.

---

## Recommendation

**Varnish** is the strongest technical choice: highest throughput, native request
coalescing, native prefix-`ban` flush, and serve-stale (`grace`) that hides Sling
restarts. Trade-offs: VCL as a new language, a RAM-bound cache to size, cold-on-
restart, and careful porting + testing of the filters. **Apache** is the
"keep what you know" option but lacks coalescing (stampede risk) and its disk
persistence caused the staleness saga. Switching is a one-line `variant:` change
once the chosen engine's image is published to GHCR.
